# Feature Specification: MCP メトリクスエクスポータ（MCP サーバー可観測性）

**Feature Branch**: `016-mcp-metrics-exporter`
**Created**: 2026-06-17
**Status**: Draft
**Input**: User description: "4つのMCPサーバー（docker-server / prometheus-server / terragrunt-server / alertmanager-server）の可観測性を実現する。MCPツールの呼び出し回数・実行時間・成功/失敗を計測し、既存のLGTM基盤（Prometheus + Grafana）で可視化する。"

## 概要

このプロジェクトの4つの MCP サーバー（docker-server / prometheus-server / terragrunt-server / alertmanager-server）は、Claude Code が必要時に起動・終了する**短命（ephemeral）なローカルプロセス**である。そのため監視基盤の他サービスとは異なり、Prometheus からの pull スクレイプで内部状態を観測できない。本機能は、各 MCP サーバーが自身のツール利用状況（呼び出し回数・実行時間・成否）を計測し、稼働中の収集パイプラインへ能動的に送出（push）することで、既存の可視化基盤上でその利用実態を観測可能にする。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - MCP ツール利用が観測可能になる (Priority: P1)

運用者（ジント）として、MCP サーバーのツールがいつ・どれだけ呼ばれ、成功したか失敗したかを、既存の可視化基盤上で確認したい。これまで MCP は「ブラックボックス」で、Claude が裏で何を実行しているのか、どのツールが多用され、どれがエラーを返しているのかを後から振り返る手段が無かった。

**Why this priority**: これが本機能の存在理由そのもの。1つの MCP サーバーでもツール利用メトリクスが収集基盤に届き、クエリできれば、それだけで「MCP が観測不能」という積年の空白が埋まる。最小の価値ある成果（MVP）。

**Independent Test**: 1つの MCP サーバー（例: prometheus-server）にメトリクス計装を入れ、ツールを数回呼び出した後、Prometheus 上で当該サーバーのツール呼び出し回数メトリクスが増加していることを確認できれば、独立して検証・価値提供が成立する。

**Acceptance Scenarios**:

1. **Given** 計装済みの MCP サーバーが Claude Code により起動されている、**When** あるツールが正常に1回呼び出される、**Then** 収集基盤上で当該サーバー・当該ツールの「呼び出し回数（成功）」が 1 増加する
2. **Given** 計装済みの MCP サーバーが稼働中、**When** あるツールがエラーで終了する、**Then** 収集基盤上で当該ツールの「呼び出し回数（失敗）」が 1 増加し、成功カウントとは区別される
3. **Given** ツールが複数回呼び出された、**When** 運用者が収集基盤でレイテンシ分布を照会する、**Then** ツール実行時間の分布（例: 中央値・上位パーセンタイル）が取得できる

---

### User Story 2 - 短命プロセスでも計測値が失われない (Priority: P1)

運用者として、MCP プロセスが短命であっても、その生存中に発生したツール呼び出しの計測値が確実に収集基盤へ届いてほしい。MCP は Claude Code がツールを使い終えると速やかに終了する。終了の瞬間に計測値がメモリ上に留まったまま消えれば、観測そのものが信頼できなくなる。

**Why this priority**: 本設計の最大の論点。push 方式は「送出する前にプロセスが死ねば計測値は失われる」という固有のリスクを抱える。この信頼性が担保されなければ US1 の数値が断片的・不正確になり、機能全体の価値が崩れる。よって US1 と同格の P1。

**Independent Test**: ツールを1回呼び出した直後に MCP プロセスを通常終了（および中断シグナル）させ、その単発の呼び出しが収集基盤に反映されることを確認できれば独立して検証できる。

**Acceptance Scenarios**:

1. **Given** ツールが1回呼び出された直後にプロセスが正常終了する、**When** 収集基盤を確認する、**Then** その1回の呼び出しが計測値に反映されている（送出前の取りこぼしが無い）
2. **Given** MCP プロセスが中断シグナル（停止要求）を受けて終了する、**When** 収集基盤を確認する、**Then** 終了直前までの計測値が送出されている
3. **Given** 収集先が一時的に到達不能、**When** MCP のツールが呼び出される、**Then** ツール本来の応答は遅延・失敗せず、計測の失敗は MCP の機能を阻害しない

---

### User Story 3 - ツール利用ダッシュボードで一望できる (Priority: P2)

運用者として、4つの MCP サーバー横断で、ツール別の呼び出し回数・レイテンシ・エラー率を1枚のダッシュボードで俯瞰したい。生のクエリを毎回書くのではなく、利用傾向と異常を視覚的に把握したい。

**Why this priority**: US1/US2 でメトリクスが収集できれば価値は成立するが、ダッシュボードがあって初めて「日常的に眺めて気づける」運用品質に至る。価値はあるが MVP の後続。

**Independent Test**: メトリクスが収集基盤に存在する状態で、ダッシュボードを開き、サーバー別・ツール別の呼び出し回数／レイテンシ／エラー率パネルが実データで描画されることを確認できれば独立して検証できる。

**Acceptance Scenarios**:

1. **Given** 複数の MCP サーバーで複数ツールが呼び出された履歴がある、**When** 運用者が MCP 可観測性ダッシュボードを開く、**Then** サーバー別・ツール別の呼び出し回数が表示される
2. **Given** 同上、**When** ダッシュボードを参照する、**Then** ツール別のレイテンシ（パーセンタイル）とエラー率が表示される

---

### Edge Cases

- **送出先が到達不能**: 収集先（収集パイプライン）がダウン／ネットワーク不通の場合でも、MCP のツール応答は遅延・失敗してはならない（計測は best-effort、本来機能を阻害しない）。
- **複数インスタンスの同時稼働**: 同じ MCP サーバーが短時間に複数回起動・終了した場合でも、各起動分の計測値が重複や取りこぼしなく合算される（カウンタの単調性が利用者視点で保たれる）。
- **極めて短命なプロセス**: 起動直後にツールを1回だけ呼んで即終了する場合でも、その1回が失われない。
- **計装対象外の内部処理での例外**: ツールハンドラ外で発生した例外（起動失敗等）は計測の対象外であり、計測機構自体がプロセスのクラッシュ原因になってはならない。
- **長時間稼働セッション**: 稀に MCP が長時間生存し続ける場合でも、定期的に計測値が送出され、最新値が収集基盤に反映され続ける。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 各 MCP サーバーは、ツール呼び出しごとに「呼び出し回数」を計測しなければならない。
- **FR-002**: 各 MCP サーバーは、ツール呼び出しの結果を成功／失敗で区別して計測しなければならない。
- **FR-003**: 各 MCP サーバーは、ツール呼び出しの実行時間（レイテンシ）を分布として計測しなければならない。
- **FR-004**: 計測値には、どの MCP サーバー（サービス名）・どのツールに由来するかを識別できる属性（ラベル）が付与されなければならない。
- **FR-005**: 各 MCP サーバーは、計測値を稼働中の収集パイプラインへ能動的に送出（push）しなければならない（pull スクレイプは構成上成立しないため）。
- **FR-006**: MCP プロセスが終了する際、メモリ上に滞留している未送出の計測値を、終了前に確実に送出（flush）しなければならない。これは正常終了・中断シグナルの両方で機能しなければならない。
- **FR-007**: 計測・送出の失敗は、MCP ツール本来の応答を遅延させたり失敗させたりしてはならない（計測は best-effort）。
- **FR-008**: 計測値は、最終的に既存の可視化基盤（Prometheus / Grafana）から照会可能でなければならない。新規の監視インフラ（新しい常駐サービス）を追加してはならない。
- **FR-009**: 4つの MCP サーバーすべてで、計測の定義・属性体系・送出方式が一貫していなければならない（共通の計装方式を再利用する）。
- **FR-010**: 運用者は、ツール別の呼び出し回数・レイテンシ・エラー率をダッシュボードで一望できなければならない。
- **FR-011**: 計測機構の導入によって、MCP サーバーの既存ツールの動作・インターフェース（入出力契約）が変化してはならない。
- **FR-012**: 計測機構は設定により無効化できなければならない（例: ローカル単体実行・テスト時に送出を止められる）。

### Key Entities

- **ツール呼び出しイベント**: ある MCP サーバーで1つのツールが実行された事実。属性として「サービス名（どの MCP）」「ツール名」「結果（成功/失敗）」「所要時間」を持つ。
- **呼び出しカウンタ**: ツール呼び出しイベントの累積回数。サービス名・ツール名・結果で分類される単調増加の数値。
- **レイテンシ分布**: ツール実行時間の分布。サービス名・ツール名で分類される。
- **MCP サービス識別子**: 各 MCP サーバーを一意に識別する名前（docker / prometheus / terragrunt / alertmanager）。全計測値に付与される。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 運用者は、任意の MCP ツールが呼び出された後、その呼び出しが収集基盤の計測値に反映されていることを確認できる（取りこぼし 0 件）。
- **SC-002**: ツールを1回だけ呼び出して即座にプロセスを終了させる検証で、その1回の呼び出しが計測値に反映される成功率が 100% である（ephemeral flush の信頼性）。
- **SC-003**: 4つの MCP サーバーすべてが、サービス名で識別可能な計測値を収集基盤へ送出している（4/4 サーバーが観測可能）。
- **SC-004**: 運用者は、1枚のダッシュボードで、サーバー別・ツール別の「呼び出し回数」「レイテンシ」「エラー率」を確認できる。
- **SC-005**: 計測機構の導入前後で、MCP ツールの応答内容・所要時間に利用者が体感できる劣化が無い（収集先が到達不能な状況でもツールが正常応答する）。
- **SC-006**: 新規の常駐監視サービスは1つも追加されていない（既存の収集パイプラインへの相乗りのみ）。

## Assumptions

- 計測値の送出先は、既に稼働中で外部到達可能な収集パイプライン（otel-collector、10.0.0.220:4317）であり、本機能のためにそのエンドポイント自体を新設する必要はない。ただし、当該パイプラインに**メトリクス用の経路（現状はトレース用経路のみ）を増設**する必要がある（これは新規常駐サービスの追加ではなく既存サービスの設定拡張とみなす）。
- MCP サーバーが Claude Code から起動される際、送出先エンドポイントに到達できるネットワーク経路が存在する。
- 計測の粒度は「ツール単位」で十分であり、ツール内部の細分化されたサブ処理までは計測対象としない（将来拡張の余地として残す）。
- 計測値の保持期間・解像度は、既存 Prometheus の設定に従い、本機能固有の長期保存要件は設けない。
- ダッシュボードは既存 Grafana のプロビジョニング機構に従って追加され、手動での画面構築は行わない。

## Out of Scope

- MCP ツール呼び出しの**分散トレーシング**（個々の呼び出しのスパン・親子関係の追跡）。本機能はメトリクス（集計値）に限定する。
- MCP が内部で呼ぶ外部コマンド（docker / ssh / curl 等）の個別計測。計測境界はツールハンドラの入口〜出口とする。
- 計測値に基づくアラート（しきい値超過通知）の定義。可視化までを範囲とし、アラート設計は将来の別機能とする。
- ツール呼び出しの引数・戻り値の内容そのものの記録（機密混入リスクを避けるため、属性は識別子と結果に限定する）。
