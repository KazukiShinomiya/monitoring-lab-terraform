# Feature Specification: Docker MCP Server

**Feature Branch**: `002-docker-mcp-server`
**Created**: 2026-03-07
**Status**: Draft

## Overview

AIアシスタント（Claude Code）が自然言語での対話を通じて、リモートサーバー上で稼働するコンテナ群の状態確認と基本的なライフサイクル操作を行えるようにする。エンジニアは従来のターミナル操作なしに、AIとの会話の中でインフラの状態把握と問題対応を完結させることができる。

---

## User Scenarios & Testing *(mandatory)*

### User Story 1 - コンテナ状態の自然言語照会 (Priority: P1)

エンジニアがAIに「今コンテナはどんな状態？」と尋ねると、AIがリモートサーバーの全コンテナ一覧・稼働状況・起動時刻を返答する。ターミナルを開かず、作業の文脈を中断せずにインフラ状態を把握できる。

**Why this priority**: 読み取りのみで副作用がなく、最も頻繁に使われる操作。これが機能するだけでAIアシスタントとしての基本価値が成立する。

**Independent Test**: AIに「コンテナの一覧を教えて」と伝えるだけで、稼働中の全コンテナ名・状態・起動経過時間が返答として得られること。

**Acceptance Scenarios**:

1. **Given** リモートサーバーで複数のコンテナが稼働している状態で、**When** AIに「コンテナの状態を確認して」と依頼する、**Then** 全コンテナの名前・状態（running/stopped等）・起動経過時間が一覧で返答される。
2. **Given** 特定のコンテナが停止している状態で、**When** AIに「全コンテナの状態を教えて」と依頼する、**Then** 停止中のコンテナも含めて全件が返答される。
3. **Given** リモートサーバーへの接続が失敗する状態で、**When** AIが状態確認を試みる、**Then** 接続エラーである旨が返答され、操作は安全に失敗する。

---

### User Story 2 - コンテナログの取得 (Priority: P1)

エンジニアが「Grafanaのログを見せて」と伝えると、AIが指定コンテナの直近ログを取得して提示する。問題の原因調査が会話の中で完結する。

**Why this priority**: 障害対応の最初のステップはログ確認であり、状態確認と同等に頻繁に必要とされる。

**Independent Test**: AIに「[コンテナ名]のログを取得して」と伝えるだけで、直近のログ出力が返答として得られること。

**Acceptance Scenarios**:

1. **Given** 対象コンテナが稼働中の状態で、**When** AIに「Prometheusのログを100行見せて」と依頼する、**Then** 直近100行のログが返答される。
2. **Given** 対象コンテナ名の指定が曖昧な場合、**When** AIが候補を提示して確認を求める、**Then** エンジニアが選択後に正しいコンテナのログが返答される。
3. **Given** 存在しないコンテナ名を指定した場合、**When** AIがログ取得を試みる、**Then** コンテナが見つからない旨のエラーが返答される。

---

### User Story 3 - リソース使用量の確認 (Priority: P2)

エンジニアが「どのコンテナが一番リソースを使ってる？」と尋ねると、AIがCPU・メモリ使用量を取得して提示する。

**Why this priority**: 定期的な健全性確認や問題調査に有用だが、ログ確認より緊急性は低い。

**Independent Test**: AIに「コンテナのリソース使用量を教えて」と伝えるだけで、各コンテナのCPU・メモリ使用量が返答として得られること。

**Acceptance Scenarios**:

1. **Given** 複数のコンテナが稼働している状態で、**When** AIに「リソース使用量を確認して」と依頼する、**Then** 全コンテナのCPU使用率とメモリ使用量が返答される。
2. **Given** リソース情報の取得に時間がかかる場合、**When** AIが取得を試みる、**Then** タイムアウト前に結果が返答されるか、タイムアウト旨が通知される。

---

### User Story 4 - コンテナの再起動（承認フロー付き） (Priority: P2)

エンジニアが「Grafanaを再起動して」と伝えると、AIが操作内容を確認提示し、エンジニアが「はい」と答えた後に再起動を実行する。誤操作を防ぐ承認ステップが必ず挟まる。

**Why this priority**: 最も安全な操作系コマンド（再起動はサービスを完全には削除しない）かつ、障害対応で頻繁に必要とされる。

**Independent Test**: AIに「[コンテナ名]を再起動して」と依頼し、確認に「はい」と答えることで、コンテナが再起動されること。

**Acceptance Scenarios**:

1. **Given** 対象コンテナが稼働中の状態で、**When** AIに「Grafanaを再起動して」と依頼する、**Then** AIは「monitoring-lab-grafana を再起動します。よろしいですか？」と確認を求める。
2. **Given** AIが再起動確認を提示した状態で、**When** エンジニアが「はい」と答える、**Then** コンテナが再起動され、完了が返答される。
3. **Given** AIが再起動確認を提示した状態で、**When** エンジニアが「いいえ」と答える、**Then** 操作はキャンセルされ、コンテナは変更されない。
4. **Given** 存在しないコンテナ名を指定した場合、**When** AIが再起動を試みる、**Then** エラーが返答され、操作は実行されない。

---

### User Story 5 - コンテナの停止・起動（承認フロー付き） (Priority: P3)

エンジニアが「New Relicを停止して」または「New Relicを起動して」と伝えると、承認確認の後にコンテナの停止または起動が実行される。

**Why this priority**: 再起動より影響範囲が大きいため優先度は低いが、メンテナンス作業で必要になる。

**Independent Test**: AIに「[コンテナ名]を停止/起動して」と依頼し、確認に「はい」と答えることで、コンテナが停止/起動されること。

**Acceptance Scenarios**:

1. **Given** 対象コンテナが稼働中の状態で、**When** AIに「[コンテナ名]を停止して」と依頼し確認に同意する、**Then** コンテナが停止され、完了が返答される。
2. **Given** 対象コンテナが停止中の状態で、**When** AIに「[コンテナ名]を起動して」と依頼し確認に同意する、**Then** コンテナが起動され、完了が返答される。
3. **Given** 承認を求められた状態で、**When** エンジニアが拒否する、**Then** 操作はキャンセルされる。

---

### Edge Cases

- リモートサーバーへの接続が切断された場合、操作系コマンドは実行されずエラーを返す。
- コンテナ名が部分一致する複数の候補がある場合、AIは候補を列挙して選択を求める。
- 既に目的の状態にあるコンテナへの操作（稼働中コンテナへの起動、停止中コンテナへの停止）は、承認フロー前に現在の状態を伝えてキャンセルする。
- 操作系コマンドの承認ステップで無応答・不明瞭な返答があった場合、操作はキャンセルされる（デフォルト安全）。
- コンテナの操作中（実行中）にタイムアウトが発生した場合、エンジニアに状態不明である旨を通知する。承認待ち中はタイムアウトしない。
- コンテナの作成・削除・イメージ操作は本機能のスコープ外であり、実行不可とする。

## Requirements *(mandatory)*

### Functional Requirements

**読み取り系**

- **FR-001**: AIはリモートサーバー上の全コンテナの名前・状態・起動経過時間を取得できること。
- **FR-002**: AIは指定されたコンテナの直近ログを取得できること（行数を指定可能。未指定時のデフォルトは100行）。
- **FR-003**: AIはリモートサーバー上の全コンテナのCPU使用率とメモリ使用量を取得できること。

**操作系**

- **FR-004**: AIはコンテナの再起動をエンジニアの承認後に実行し、完了後にコンテナの実際の状態（running/stopped等）を確認して報告すること。
- **FR-005**: AIはコンテナの停止をエンジニアの承認後に実行し、完了後にコンテナの実際の状態を確認して報告すること。
- **FR-006**: AIはコンテナの起動をエンジニアの承認後に実行し、完了後にコンテナの実際の状態を確認して報告すること。
- **FR-007**: 操作系コマンドはすべて実行前に「操作内容 + コンテナ名」を明示した確認メッセージを表示すること。
- **FR-008**: 確認メッセージに対する明確な同意なしには、操作系コマンドは実行されないこと。

**安全制約**

- **FR-009**: コンテナの作成・削除・イメージのpull/削除は実行できないこと（スコープ外）。
- **FR-010**: リモートサーバーへの接続失敗時は、操作系コマンドを実行せずエラーを返すこと。

### Key Entities

- **コンテナ**: 名前・状態・起動時刻・CPUおよびメモリ使用量・ログ出力を持つ管理対象の実行単位。
- **承認フロー**: 操作系コマンド実行前に必ず経由する確認ステップ。同意・拒否の2状態を持つ。タイムアウトは設けず、次のユーザー入力まで待機する。

---

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: エンジニアがコンテナの状態を確認するまでの手順が、従来のターミナル操作と比較して50%以上削減される（コマンド入力不要、会話で完結）。
- **SC-002**: コンテナ情報の返答が、依頼から10秒以内に得られること。
- **SC-003**: 操作系コマンドの承認ステップが100%のケースで発動すること（誤操作ゼロ）。
- **SC-004**: 接続エラーや不正な入力が発生した場合、100%のケースでエンジニアへの適切なエラー通知が行われること（サイレント失敗ゼロ）。

## Clarifications

### Session 2026-03-07

- Q: 承認フローのタイムアウト時間 → A: タイムアウトなし。次のユーザー入力まで待機し、明示的な拒否のみキャンセルとみなす。
- Q: ログ取得のデフォルト行数 → A: 100行。運用後に調整可能な想定。
- Q: MCPサーバーの動作環境 → A: Dockerコンテナ。SSH鍵はWSL2の ~/.ssh/ からマウント（Terragruntコンテナと同方式）。
- Q: 操作後の状態確認 → A: 操作完了後にコンテナの実際の状態を確認し、running/stopped等を報告する。
- Q: 既に目的の状態にあるコンテナへの操作 → A: 事前に状態確認し「既にrunning/stoppedです」と返す。承認フローに入らず操作しない。

## Assumptions

- リモートサーバー（10.0.0.220）へのSSH接続は既存の認証基盤（SSH鍵）を利用する。
- 操作対象は `monitoring-lab-*` プレフィックスを持つコンテナ群とする。
- コンテナ名の完全一致が取れない場合は部分一致候補を提示するが、最終選択はエンジニアが行う。
- 承認フローの「同意」は「はい」「yes」「y」等の肯定的な返答とし、それ以外はすべてキャンセルとみなす。
- 本MCPサーバーはモノレポ内 `mcp/docker-server/` に配置し、Dockerコンテナとして起動する。Claude CodeはMCPクライアントとしてコンテナに接続する。SSH鍵はコンテナ起動時にWSL2の `~/.ssh/` からマウントする（既存のTerragruntコンテナと同方式）。

## Out of Scope

- コンテナの作成・削除・イメージ操作（IaCで管理するため）
- 複数サーバーへの同時接続
- 操作履歴の永続化・監査ログ
- Webインターフェースやダッシュボード化
